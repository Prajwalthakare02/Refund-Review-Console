# Database & Data Engine Rules — Refund Review Console

## Executive Data Architecture Summary
The Data Engine (`ingest.py` and `state_engine.py`) parses raw CSV and JSONL exports, applies clean transformation pipelines, and materializes a mathematically provable state for every order.

---

## 1. Data Schema & Models

### Order Entity (`orders.csv`)
- `order_id`: String (Primary Key)
- `customer_id`: String
- `currency`: String (`INR` | `USD`)
- `total_amount_minor`: Integer (Converted from decimal `total_amount`)
- `placed_at_utc`: Datetime ISO-8601 string
- `channel`: String (`web` | `android` | `ios`)
- `region`: String (`IN`)

### Event Entity (`events.jsonl`)
- `event_id`: String (Primary Key for deduplication)
- `type`: String (`refund.requested` | `refund.succeeded` | `refund.failed` | `chargeback.opened`)
- `order_id`: String
- `refund_id`: String (Optional, null for `chargeback.opened`)
- `currency`: String
- `amount_minor`: Integer (Normalized from `amount_minor` or decimal `amount`)
- `occurred_at_utc`: Datetime ISO-8601 string (Canonical event timestamp)
- `received_at_utc`: Datetime ISO-8601 string (Ingestion timestamp)
- `source`: String (`gw_primary` | `gw_upi` | `legacy_gw`)
- `reason`: String (Optional)
- `failure_code`: String (Optional: `bank_timeout`, `invalid_vpa`, `beneficiary_account_closed`)

## 2. The 12 Anomaly Resolution Rules

### Rule 1: Event Deduplication (Overnight Relay Replays)
- **Problem**: `evt_0001` appears multiple times in raw export.
- **Rule**: Track processed `event_id`s in a set. Discard any second or subsequent event sharing an identical `event_id`.

### Rule 2: Timezone Normalization (Legacy Gateway IST vs UTC)
- **Problem**: `legacy_gw` events provide naive timestamps (`"2026-08-01 05:54:00"`) without timezone designation.
- **Rule**: Treat naive timestamps as Indian Standard Time (`Asia/Kolkata` / `+05:30`). Convert all timestamps to UTC ISO-8601 strings and sort events strictly by normalized `occurred_at_utc`.

### Rule 3: Currency Unit Normalization (Minor Units)
- **Problem**: `gw_primary` and `gw_upi` report `amount_minor` (paise/cents), while `legacy_gw` reports decimal `amount` (e.g. `823.55`).
- **Rule**: Convert all amounts to integer minor units (`round(amount * 100)`). All calculations occur strictly in minor units to eliminate floating-point precision errors.

### Rule 4: Negative Refund Amount Handling (`ord_1022`)
- **Problem**: `evt_0043` carries `amount_minor: -35000` (reason: `"correction"`).
- **Rule**: Process negative refund requests literally. A negative request reduces pending/refunded totals, representing a valid gateway adjustment.

### Rule 5: Zero Refund Amount Handling (`ord_1021`)
- **Problem**: `evt_0042` carries `amount_minor: 0` (reason: `"adjustment"`).
- **Rule**: Include zero-amount events in order timelines for auditability, but exclude them from monetary calculations.

### Rule 6: Currency Mismatch Surfacing (`ord_1024`)
- **Problem**: `ord_1024` total is `7200.00 INR` in `orders.csv`, but event `evt_0044` specifies `USD` currency.
- **Rule**: Trust the event's explicit currency for that refund record. Render a visual warning badge `⚠️ Currency Mismatch` in the console.

### Rule 7: Over-Refund Detection (`ord_1003` & `ord_1030`)
- **Problem**: Total succeeded/requested refunds exceed original order total (e.g. `ord_1003` refunded ₹1,100 on ₹999 order).
- **Rule**: Calculate and render real amounts truthfully. Allow `remaining_refundable_minor` to be negative. Render an `⚠️ Over-refunded` warning pill.

### Rule 8: Terminal State Reversal (`rfnd_5050`)
- **Problem**: `rfnd_5050` transitioned `requested` -> `succeeded` -> `failed` (`beneficiary_account_closed`).
- **Rule**: Chronological event ordering determines final state. A `failed` event occurring after `succeeded` indicates money bounced back; mark refund status as `failed` and return funds to refundable pool.

### Rule 9: Chargeback & Double-Loss Risk (`ord_1014`)
- **Problem**: Order `ord_1014` had a successful refund of ₹5,600, followed by an open chargeback `CB-77401`.
- **Rule**: Chargebacks do not reduce refund totals directly. If an order contains both a successful refund AND an active chargeback, surface a `🚨 Double Loss Risk` alert badge for Finance.

### Rule 10: Missing Order Placeholders (`ord_1008`)
- **Problem**: Event `evt_0020` references `ord_1008`, which is absent from `orders.csv`.
- **Rule**: Create a placeholder order record with `total_amount_minor = null`. Display events in timeline with badge `⚠️ Order Missing from Export`.

### Rule 11: Cross-Gateway Duplicate Relays (`ord_1011`)
- **Problem**: Near-identical refund requests generated by `legacy_gw` and `gw_upi` at the exact same timestamp.
- **Rule**: Distinct `refund_id`s represent separate entities. Process both independently and let human agents review via the console.

### Rule 12: Ingestion Latency & Out-of-Order Events (`ord_1005`)
- **Problem**: `received_at` for `refund.succeeded` is logged earlier than `received_at` for `refund.requested`.
- **Rule**: Ignore `received_at` for state machine ordering. Always sort event timelines by `occurred_at_utc`.

### Rule 13: Support Queue Time Window
- **Problem**: Rahul's agents need to see all orders with refund activity in the last 7 days from PINNED_NOW, but some old orders may have recent events.
- **Cutoff**: `SUPPORT_QUEUE_CUTOFF = 2026-08-04T04:30:00Z` (exactly 7 days prior to `PINNED_NOW` UTC: `2026-08-11T04:30:00Z`).
- **Rule**: An order qualifies for the Support History Queue if **either**:
  1. `order.placed_at_utc >= SUPPORT_QUEUE_CUTOFF`, **OR**
  2. Any event belonging to that order has `occurred_at_utc >= SUPPORT_QUEUE_CUTOFF`.
- This ensures old orders with recent refund activity are still visible to support agents.

### Rule 14: High-Value Threshold Constants
- **Problem**: Priya requires approval gates on high-value refund requests before outflow.
- **Rule**: A refund is flagged as high-value if its `amount_minor` meets or exceeds the following thresholds:
  - **INR**: `HIGH_VALUE_INR_MINOR = 5_000_000` (₹50,000 × 100 paise)
  - **USD**: `HIGH_VALUE_USD_MINOR = 50_000` ($500 × 100 cents)
- High-value refunds receive a prominent `🔴 HIGH VALUE` badge in both queue and detail views.

### Rule 15: Agent Decision Overrides
- **Problem**: After an agent approves or rejects a pending refund in the console, the system must reflect that decision in all state calculations.
- **Rule**: Manual agent decisions take **absolute precedence** over raw gateway pending state:
  - **Approved**: The refund transitions from `pending_payout` to `approved` state. It remains counted in `pending_payout_minor` (money is still expected to leave) but is no longer actionable in the Finance Queue.
  - **Rejected**: The refund is removed from `pending_payout_minor` entirely. The rejected amount is **not** deducted from `remaining_refundable_minor` (the money stays with the company; it was never sent).
  - **No Decision (default)**: The refund remains in `pending_payout_minor` and is actionable in the Finance Queue.
- Decisions are stored with `refund_id`, `action`, `reason`, `idempotency_key`, and `recorded_at`.

## 3. Order State Derivation Formula

```python
# Constants
PINNED_NOW_UTC = "2026-08-11T04:30:00Z"
SUPPORT_QUEUE_CUTOFF = "2026-08-04T04:30:00Z"  # 7 days prior
HIGH_VALUE_INR_MINOR = 5_000_000   # ₹50,000 in paise
HIGH_VALUE_USD_MINOR = 50_000      # $500 in cents

for order in orders:
    total_paid = order.total_amount_minor
    refunded_succeeded = 0
    pending_payout = 0
    
    for refund_id, event_chain in order.events_grouped_by_refund_id():
        # Sort chain by occurred_at_utc (Rule 12: never by received_at)
        sorted_chain = sorted(event_chain, key=lambda e: e.occurred_at_utc)
        latest_event = sorted_chain[-1]
        
        # Rule 15: Agent decisions override raw state
        manual_decision = get_agent_decision(refund_id)
        
        if manual_decision == "rejected":
            # Rejected: remove from pending, do NOT deduct from remaining
            continue
        elif latest_event.type == "refund.succeeded":
            refunded_succeeded += latest_event.amount_minor
        elif latest_event.type == "refund.failed":
            pass  # Money returned to refundable pool
        elif latest_event.type == "refund.requested":
            # Still pending (or approved but awaiting gateway confirmation)
            pending_payout += latest_event.amount_minor
            
    remaining_refundable = total_paid - refunded_succeeded - pending_payout
```
